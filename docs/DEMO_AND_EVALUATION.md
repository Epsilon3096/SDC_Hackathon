# Demonstration and evaluation

## Six-minute demonstration

1. **The decision.** A quality inspector has limited weekly study time and needs a justified next learning action. Explain the Malaysian TalentCorp E&E context and keep upgraded QA as a valid route.
2. **The person.** Choose Aina or Farid; edit one skill or weekly-hours constraint; save it. Explain synthetic data, selected-skill coverage and unknown entry requirements.
3. **The baseline.** Compare the three routes. Open a contribution breakdown and identify one gap. Adopt a learning plan and note the evidence snapshot it uses.
4. **The evidence.** Inspect Intel's source, correct December 2023 date, exact passage and limited interpretation. Approve it with a reason, then separately publish a new snapshot. Explain that weight deltas are team modelling assumptions.
5. **The change.** Compare baseline/current results and moderate/faster adoption. A reduced alignment score means the requirements became more demanding, not that the worker lost skills. Inspect changed learning priority. Do not claim the plan order changed if it did not. Adopt the revised plan only after comparison.
6. **The restraint.** Reject the synthetic retail chatbot mapping and the related-but-insufficient research mapping. Confirm the active snapshot and accepted plan stay unchanged. Show a genuine source refresh if available; otherwise state the fetch error and demonstrate preserved state without calling it live success.
7. **The evidence of quality.** Show actual test results, source limitations and any measured usability result. Explain RunPod's current unconfigured status and planned narrow responsibility honestly.

Suggested timing: problem 40s; profile 40s; comparison 60s; evidence/publication 80s; changed plan 60s; restraint 40s; validation 40s.

## Small usability pilot protocol

No planning-time improvement has been measured yet. The number 42 seconds is not a result.

Use at least five independent testers if feasible. Give each two equivalent synthetic worker tasks, one with a static source/resource catalogue and one with ShiftBridge. Counterbalance order to limit learning effects. Record time from task presentation until the tester selects a source-backed, prerequisite-valid next step. Use the same success rubric in both conditions.

Record anonymised tester ID, task/version, condition/order, seconds, correct/incorrect, prerequisite mistakes, source-citation correctness and any help provided. Do not collect CVs or sensitive personal data. Internal developer rehearsals must be labelled separately.

Report sample size, individual observations, median time, success rate and failures. Calculate percentage reduction only from observed nonzero baseline time. A small convenience sample can inform usability; it cannot demonstrate employment, income or emissions benefits.

## Release checks

- `npm run check`, `npm test`, `npm run build` pass on the final source.
- No secrets, vouchers, database state or node_modules in the distribution.
- Source dates distinguish publication precision from retrieval dates.
- No fabricated vacancies, qualifications, provider durations or certificate prices.
- Snapshot rejection and model/source failures preserve the previous accepted state.
- Sources and learning resources open from a fresh browser.
- Mobile and desktop flows tested with real API state.
- Published URL and persistence verified separately from the local build.
- Real GPU use, if later enabled, is evidenced separately from mocked tests.
- Competition write-up uses the required templates; claims and AI/tool declarations match the implementation.
