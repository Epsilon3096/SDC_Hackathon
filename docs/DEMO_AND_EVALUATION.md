# Demonstration and evaluation

## Six-minute demonstration

Start with **Guided demo** in the application header. It creates or resumes an isolated rehearsal; **Restart this demonstration** offers an explicit reset of that rehearsal only. The ordinary workspace is preserved. Use the guide's actions to return to Farid, QA and moderate adoption. Hide the guide temporarily when presenting the calculation or learning sequence.

The demonstration seeds Farid with documentation level 1, quality-data level 0, four hours/week and RM 0. Show these assumptions. This is a constructed comparison with real application/database operations, not a real worker result or a live-news simulation. Each guide milestone is derived from stored decisions. Use the real review and publish controls; no step silently performs them.

1. **The decision.** A quality inspector has limited weekly study time and needs a justified next learning action. Explain the Malaysian TalentCorp E&E context and keep upgraded QA as a valid route.
2. **The person.** Choose Aina or Farid; edit one skill or weekly-hours constraint; save it. Explain synthetic data, selected-skill coverage and unknown entry requirements.
3. **The baseline.** Compare the three routes. Open a contribution breakdown and identify one gap. Adopt a learning plan and note the evidence snapshot it uses.
4. **The evidence.** Inspect Intel's source, correct December 2023 date, exact passage and limited interpretation. Approve it with a reason, then separately publish a new snapshot. Explain that weight deltas are team modelling assumptions.
5. **The change.** Compare baseline/current results and moderate/faster adoption. A reduced alignment score means the requirements became more demanding, not that the worker lost skills. Inspect changed learning priority. Do not claim the plan order changed if it did not. Adopt the revised plan only after comparison.
6. **The restraint.** Reject the synthetic retail chatbot mapping and the related-but-insufficient research mapping. Confirm the active snapshot and accepted plan stay unchanged. Show a genuine source refresh if available; otherwise state the fetch error and demonstrate preserved state without calling it live success.
7. **The evidence of quality.** Show actual test results, source limitations and any measured usability result. Explain RunPod's narrow relevance-triage responsibility and actual verification status. An endpoint being created or building does not prove completed inference; only show real completed results once verified.

After adoption, use **Download decision brief** on the saved learning plan. The text includes the original profile, assessment, model version, constraints, source references, ordered practice and limitations. A new profile edit must not rewrite that original decision. Legacy plans without captured assessments say so. Do not mark a learning exercise complete merely to make progress look better; rehearsal checkboxes represent simulated activity only if explicitly demonstrated as such.

Suggested timing: problem 40s; profile 40s; comparison 60s; evidence/publication 80s; changed plan 60s; restraint 40s; validation 40s.

## Optional visible plan-order change

For a second synthetic case, edit Farid's documentation level to 1 and quality-data level to 0, and save. The same engine changes the baseline sequence documentation → data → AI → root cause to AI → documentation → data → root cause after the reviewed Intel mapping is published. Keep the edits visible; this is a constructed demonstration, not an observed worker outcome. Aina's default QA alignment changes 65.33 to 61.59 under faster adoption, while her skill profile stays unchanged. These are deterministic model outputs, not measured social impact.

## Optional correction and continuity demonstration

After publishing a reviewed rule, open Evidence Studio and select the active rule for retirement. Enter a reason and publish the next snapshot. Its adjustment disappears from the current assessment, while the earlier snapshot and accepted plan remain unchanged. To replace a rule with a weaker interpretation, first create and approve the revised mapping, then publish it together with retirement of the old mapping. Do not add the weaker mapping alone: the model deliberately keeps the strongest duplicate adjustment among active rules.

For schedule continuity, adopt a plan at four hours per week, then edit the profile to eight hours. The saved plan still shows the original four-hour pace until the new suggestion is adopted. Plans created before pace capture was implemented say that the original pace was not recorded; the app does not infer it from today's profile.

Completion belongs to each saved plan. A new revision first carries valid completed steps from the same worker, role and scenario. Only the first plan in a scenario falls back to another plan for that worker and role. Prerequisite validation still applies.

## Small usability pilot protocol

No planning-time improvement has been measured yet. The number 42 seconds is not a result.

Use at least five independent testers if feasible. Give each two equivalent synthetic worker tasks, one with a static source/resource catalogue and one with ShiftBridge. Counterbalance order to limit learning effects. Record time from task presentation until the tester selects a source-backed, prerequisite-valid next step. Use the same success rubric in both conditions.

Record anonymised tester ID, task/version, condition/order, seconds, correct/incorrect, prerequisite mistakes, source-citation correctness and any help provided. Do not collect CVs or sensitive personal data. Internal developer rehearsals must be labelled separately.

Report sample size, individual observations, median time, success rate and failures. Calculate percentage reduction only from observed nonzero baseline time. A small convenience sample can inform usability; it cannot demonstrate employment, income or emissions benefits.

## Release checks

- `npm run check`, `npm test`, `npm run build` pass on the final source.
- No secrets, vouchers, database state or node_modules in the distribution.
- Source dates distinguish publication precision from retrieval dates.
- No fabricated vacancies, qualifications, provider durations or certificate prices.
- Snapshot rejection and model/source failures preserve the previous accepted state.
- Sources and learning resources open from a fresh browser.
- Mobile and desktop flows tested with real API state.
- Published URL and persistence verified separately from the local build.
- Real GPU use, if later enabled, is evidenced separately from mocked tests.
- Competition write-up uses the required templates; claims and AI/tool declarations match the implementation.
